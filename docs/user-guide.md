# AgentHub 사용자 및 관리자 가이드

AgentHub는 폐쇄망(Offline-Ready) 환경에 최적화된 **엔터프라이즈 AI Agent 런타임 플랫폼**입니다.  
사용자별 영속 워크스페이스(PVC)와 격리된 Kubernetes Agent Pod(OpenCode, Hermes)를 손쉽게 배포하고, MCP(Model Context Protocol) 도구 및 LLM 모델을 중앙에서 통제합니다.

### 정의 내보내기 / 가져오기 (GitOps)

에이전트 정의는 YAML 파일로 내보내고 다시 가져올 수 있습니다. 형상 관리 저장소에 넣어 리뷰하거나, 개발 클러스터의 정의를 운영 클러스터로 옮길 때 사용합니다.

- **내보내기**: `내 에이전트` 목록의 내려받기 아이콘을 누르면 `<이름>.yaml` 로 저장됩니다.
- **가져오기**: 목록 상단의 *정의 가져오기* 로 YAML 파일을 선택합니다.
- 참조(런타임 프로파일·작업공간·모델·MCP 번들)는 **이름** 으로 기록됩니다. 가져오는 클러스터에 같은 이름이 없으면 무엇이 없는지 알려주고 가져오기를 중단합니다. 조용히 비워둔 채 만들지 않습니다.
- 같은 이름의 정의를 다시 가져오면 **갱신** 되고, 이름을 바꾸면 **새 에이전트** 로 만들어집니다.
- 소유자·버전·시각과 모든 비밀값은 파일에 포함되지 않습니다. 런타임 유형은 파일에 다르게 적어도 변경되지 않습니다.

## 5. Agent 런타임 라이프사이클 & 세션 게이트웨이

![런타임 라이프사이클 관리](screenshots/12_runtimes_management.png)

### 5.2 Session Gateway
OpenCode나 Hermes와 같은 네이티브 Web UI에 접근할 때 1회용 런치 티켓(One-Time Launch Ticket)을 발급하여 안전한 격리 세션을 생성합니다.

세션이 열리는 주소는 관리자 설정에 따라 두 가지입니다.

- **Runtime Base Domain을 설정한 경우(권장)**: `https://<runtimeId>.agents.company.local/` 처럼 Runtime마다 전용 Origin을 사용합니다. Wildcard DNS와 인증서가 필요하지만 Runtime UI가 Portal과 Origin을 공유하지 않습니다.
- **설정하지 않은 경우**: `https://<포털주소>/<runtimeId>/` 경로로 같은 세션이 열립니다. 별도 DNS 준비 없이 바로 쓸 수 있으며 런치 티켓·세션 만료·감사 로그는 동일하게 적용됩니다.

![세션 게이트웨이 콘솔](screenshots/13_sessions_gateway.png)

## 6. Multi-Agent 워크플로우 DAG

복수의 전문 에이전트(개발, 리뷰, 배포, 데이터분석 등) 간의 협업 그래프(DAG)를 설계합니다. `워크플로` 화면 상단의 **사용법 안내**에 아래 절차가 요약되어 있으므로, 화면을 보면서 그대로 따라 할 수 있습니다.

![Multi-Agent Workflow 빌더](screenshots/14_workflows_builder.png)

### 4단계로 시작하기

1. **에이전트를 준비합니다.** 단계 하나가 에이전트 하나이며, 각 단계는 그 에이전트의 지시문과 **연결된 모델**로 실행됩니다. 모델이 연결된 에이전트가 2개 이상 있어야 협업이 됩니다.
2. **실행 방식을 고릅니다.** 만들기 화면의 카드에 각 방식이 무엇을 하고 언제 쓰는지 적혀 있습니다. `예시로 시작` 버튼을 누르면 이름·방식·단계 수가 미리 채워집니다.
3. **단계와 한도를 정합니다.** 실행 순서대로 에이전트를 넣고 호출·시간 한도를 정합니다. 저장 시 소유권·순환 참조·깊이·병렬 한도를 서버가 다시 검사하므로 잘못된 그래프는 저장되지 않습니다.
4. **실행하고 기록을 봅니다.** `실행` 을 누르면 이번에 처리할 요청 내용을 입력받고(예시 요청 넣기 버튼 제공), 끝나면 단계별 출력·소요 시간과 표결·검토 결과를 그대로 보여줍니다.

> 워크플로는 에이전트의 런타임 Pod가 아니라 **각 에이전트에 연결된 모델 API로 직접 실행**됩니다. 런타임을 켜 두지 않아도 실행되지만, 작업공간 파일이나 MCP 도구는 사용하지 않습니다. 파일을 다루거나 도구가 필요한 일은 `작업 대기열` 로 맡기세요.

### 실행 방식 선택 기준

| 방식 | 하는 일 | 이럴 때 |
| --- | --- | --- |
| 순차 실행 (Sequential) | 앞 단계의 답을 다음 단계가 이어받고, 마지막 단계의 결과가 최종 답 | 조사 → 초안 → 검토처럼 순서가 있는 일 |
| 병렬 실행 (Parallel) | 모든 단계가 같은 요청을 동시에 받고, 각자의 답을 모아 보여줌 | 같은 자료를 여러 관점에서 동시에 볼 때 |
| 라우터 (Router) | 첫 단계가 분기를 고르고, 선택되지 않은 분기는 건너뜀 | 요청 종류에 따라 담당이 갈릴 때 |

| 감독 검토 (Supervisor) | 마지막 단계가 결과를 검토해 승인하거나 지목한 에이전트에게 보완 요청(최대 2회) | 결과 품질을 한 번 걸러야 할 때. 모든 단계가 하나의 마지막 단계로 모여야 동작 |
| 리뷰 (Reviewer) | 감독 검토와 동일한 동작(이전 이름) | 기존 워크플로 유지용. 새로 만들 때는 감독 검토 사용 |
| 합의 표결 (Consensus) | 같은 질문을 각자 독립적으로 받고 `VOTE` 로 표결 | 판단이 갈리는 문제를 표로 정할 때. 단계 연결은 무시됨 |

- **가드레일 검증**: 최대 깊이(Max Depth), 최대 호출 횟수(Max Calls), 순환 참조(Cycle)를 자동 검사합니다.
- **라우터 결정 방식**: 라우터에게는 선택 가능한 분기 id 목록이 주어지고, 모델은 그 id 중에서만 고른 JSON으로 답합니다(스키마 강제). 이름이 문장에 언급되었다는 이유로 분기가 선택되는 일은 없으며, 선택 결과·이유·검증 여부는 실행 기록의 *분기 결정* 에 남습니다. 읽을 수 없는 답이 오면 모든 분기를 실행하고 그 사실을 기록에 남깁니다.
- **완료 판정도 같은 방식**: LLM 판정은 `{passed, reason, unmet}` JSON으로만 답하도록 스키마로 제한되며, `unmet` 에는 실제로 설정된 완료 조건만 넣을 수 있습니다. 설정되지 않은 조건을 지적하면 판정에서 제외되고 사유에 명시됩니다. 판정 결과를 해석할 수 없으면 통과가 아니라 실패로 처리합니다.

![새 워크플로우 생성 드로어](screenshots/15_workflow_create_drawer.png)

![검증 완료된 워크플로우 목록](screenshots/16_workflow_created_list.png)

### 감독자(Supervisor) 모드

한 에이전트가 다른 에이전트들의 결과를 검토합니다. 모든 단계가 하나의 마지막 단계로 모이는 그래프일 때만 동작하며, 그 마지막 단계가 감독자가 됩니다.

- 감독자는 결과가 충분하면 `APPROVE`, 보완이 필요하면 `REVISE: <에이전트> — <요청>` 을 적습니다. 이 안내는 플랫폼이 자동으로 붙입니다.
- 지목된 에이전트만 그 요청을 받아 다시 실행하고, 감독자가 새 결과를 다시 검토합니다. 개정된 답변이 실행 기록에 남습니다.
- 검토는 최대 2회로 제한됩니다. 끝내 합의되지 않으면 **보완 요청 남음** 으로 종료되며, 승인으로 처리하지 않습니다.
- 재실행도 최대 에이전트 호출 수에 포함됩니다.

### 합의(Consensus) 모드

여러 에이전트에게 **같은 질문**을 독립적으로 던지고 표결로 결론을 내립니다. 다른 모드와 달리 단계 간 연결은 무시되므로, 어떤 에이전트도 다른 에이전트의 답을 먼저 보지 않습니다.

- 각 참여자는 근거를 설명한 뒤 마지막 줄에 `VOTE: <결론>` 을 적습니다. 이 안내는 플랫폼이 자동으로 붙입니다.
- 집계는 모델이 아니라 플랫폼이 직접 계산하므로 결과가 재현 가능합니다. 대소문자·띄어쓰기·문장부호 차이는 같은 표로 봅니다.
- 결과는 **만장일치 / 다수결 / 동률 / 합의 없음** 중 하나로 표시되며, 소수 의견과 기권도 그대로 남습니다. 동률은 합의로 처리하지 않습니다.
- `VOTE` 를 적지 않은 참여자는 기권으로 기록되고 분모에서 빠집니다.

### 7.9 런타임 유형 고르기와 "런타임에서 이어받기"

에이전트를 만들 때 어떤 런타임을 고를지는 *카탈로그 ▸ 런타임 유형 비교* 에서 확인할 수 있습니다. 각 런타임의 작업공간 경로, 브라우저 편집기·터미널 유무, MCP 도구 전달 여부, 그리고 **하지 못하는 일**까지 함께 표시됩니다(설명은 플랫폼이 직접 제공하므로 화면과 실제 배포가 어긋나지 않습니다).

| | OpenCode | Hermes | Qwen Paw | Langflow |
|---|---|---|---|---|
| 잘하는 일 | 코드 수정·테스트·스크립트 | 여러 단계 자율 조사, 장기 기억 | 개인 업무 자동화, 스킬 실험 | 흐름을 그려서 만드는 파이프라인 |
| 브라우저 작업 | 편집기 + 터미널 | 대시보드 + 터미널 | 앱 화면 | 흐름 편집기 (터미널 없음) |
| MCP 도구 | 런타임 설정에 자동 등록 | 런타임 설정에 자동 등록 | 전달되지 않음 | 전달되지 않음 (흐름 안에서 직접 연결) |
| 공개 방식 | 자체 인증 | 플랫폼 프록시 | 플랫폼 프록시 | 플랫폼 프록시 (Runtime 전용 도메인 필요) |
| 자동 실행 | 추론 루프 + 인계 | 추론 루프 + 인계 | 추론 루프 + 인계 | **저장한 흐름을 그대로 실행** |

> **Langflow 두 가지 전제.** ① 이미지가 다릅니다 — Langflow Agent를 쓰려면 `agenthub-langflow` 이미지를 별도로 적재해야 합니다(오프라인 설치 문서 참조). ② 하위 경로로 서비스할 수 없습니다 — *관리자 ▸ 설정 ▸ Runtime 세션* 에서 **Runtime Base Domain** 을 설정한 사이트에서만 흐름 편집기를 열 수 있고, 설정되지 않은 사이트에서는 이유를 표시하며 열기를 거부합니다(빈 화면을 보여주지 않기 위해서입니다).

![런타임 인계 상태의 작업 대기열](screenshots/37_tasks_handoff.png)

**자동 실행과 런타임은 다릅니다.** `작업 대기열`의 자동 실행은 모델과 글로만 주고받는 루프여서 파일을 직접 편집하거나 명령을 실행하지 못합니다. 그래서 자동 실행 프롬프트에는 이 사실이 명시되고("하지 않은 일을 했다고 쓰지 마세요"), 그런 일이 남으면 에이전트가 **런타임 인계**로 넘깁니다.

- 인계된 작업은 **실패가 아니라 대기** 상태이며 재시도 횟수를 쓰지 않습니다. 소유자에게 알림이 가고, `task.handoff` 이벤트로 Trigger를 걸 수도 있습니다.
- 작업 행의 **런타임 열기**(터미널 아이콘)를 누르면 에이전트가 작업하던 **같은 작업공간**이 브라우저로 열립니다. 런타임이 꺼져 있으면 자동으로 시작합니다.
- 직접 마무리한 뒤 **완료 처리**(체크 아이콘)에서 완료/취소와 기록을 남깁니다. 그 기록이 작업의 마지막 설명이 되고, 감사 로그(`task.resolve`)에도 남습니다.
- 인계는 **영속 작업공간이 연결된 에이전트**에만 제안됩니다. 작업공간이 없으면 넘겨도 이어받을 곳이 없기 때문입니다.

![Agent 평가 및 벤치마크](screenshots/19_evaluation_benchmarks.png)

### 8.1 버전 기록과 운영 승격
저장은 곧 배포였습니다. 18시에 고친 정의가 02시 예약 실행에 그대로 쓰였고, 잘못 고쳤을 때 되돌릴 방법은 예전 내용을 기억하는 것뿐이었습니다. 이제 저장할 때마다 그 시점의 정의가 버전으로 남고, 그중 하나를 **운영 승격** 할 수 있습니다.

에이전트 목록의 **버전 · 운영 승격**(시계 아이콘) 버튼에서 사용합니다.

1. **저장하면 버전이 남습니다** — 생성·수정·YAML 가져오기 모두 그 시점의 정의(지시문, 모델, MCP 번들, 보안·네트워크 프로파일, 작업공간)를 함께 보관합니다.
2. **사전검증은 버전에 붙습니다** — `사전검증` 화면에서 실행한 결과는 검사한 정의 버전에 기록됩니다. 결과 카드와 버전 목록 모두에 버전 번호가 표시됩니다.
3. **통과한 버전을 승격합니다** — 통과 결과가 없는 버전은 승격이 거절됩니다. 관리자는 **사유를 적어야** 건너뛸 수 있고, 그 사유는 `검증 생략 승격: …` 으로 승격 기록과 감사 로그에 남습니다.
4. **게이트를 켜면 승격본만 실행됩니다** — *승격된 정의만 실행* 을 켜 두면 현재 정의가 승격본과 다를 때 작업 생성이 409로 즉시 거절되고, 이미 예약돼 있던 작업은 실패가 아니라 **승격 대기** 상태로 보류됩니다. 보류된 작업은 재시도 횟수를 쓰지 않고 워커 자리도 차지하지 않으며, 승격하거나 이전 버전을 복원하는 순간 자동으로 큐에 돌아갑니다(승격 결과에 “대기 중이던 작업 N건이 다시 실행됩니다”로 표시됩니다). 게이트는 **기본값이 꺼짐** 이므로 켜지 않은 에이전트는 지금까지와 똑같이 동작합니다.
5. **문제가 생기면 복원합니다** — *이 정의로 복원* 은 과거 정의를 **새 버전** 으로 다시 씁니다. 카운터를 되감지 않으므로 v4로 남은 실행 기록은 계속 v4를 가리킵니다. 승격돼 있던 버전을 복원하면 그 자리에서 다시 승격되어 운영이 바로 열립니다.

> 실행 중인 Runtime Pod는 복원 직후가 아니라 **재시작한 뒤** 새 정의로 뜹니다. 게이트는 정의가 승격됐는지만 보고, 승격본을 대신 실행해 주지는 않습니다. Pod·도구·작업공간은 모두 현재 정의로 만들어지므로, 옛 지시문을 새 Pod에 물려 실행하면 아무도 설명할 수 없는 실행이 되기 때문입니다.

## 10. 자율 실행 & 작업 승인

Agent에 **목표(Goal)** 를 설정하면 사람이 지켜보지 않아도 스스로 작업을 수행합니다. 대화형 사용 방식은 그대로 유지되며, 두 방식을 동시에 사용할 수 있습니다.

- **목표 설정**: 에이전트 상세 화면의 *목표* 패널에서 성공/실패 조건, 최대 단계 수, 완료 판정 방식(에이전트 선언 · 규칙 · 심판 모델 · 복합)을 정의합니다.
- **실행 계획**: 계획 수립 방식을 `플랫폼`으로 두면 작업 시작 전에 단계별 계획을 세우고, 실행 기록 화면에서 계획과 실제 수행 내역을 나란히 확인할 수 있습니다. `런타임 위임`은 OpenCode·Hermes 자체 에이전트 루프에 계획을 맡깁니다.
- **실행 방식(추론 루프 / 흐름 실행)**: Langflow 런타임 Agent에는 목표 설정에 *실행 방식* 이 하나 더 있습니다.
  - `추론 루프` — 기존 방식입니다. 모델과 글로 주고받으며 진행하고, 파일 편집이나 명령 실행이 필요하면 사람에게 인계합니다.
  - `흐름 실행` — Runtime에 저장된 Langflow 흐름을 그대로 실행합니다. 작업의 제목·입력과 목표·제약이 흐름의 입력으로 들어가고, 흐름의 출력이 실행 기록의 단계와 완료 판정에 사용됩니다. 산출물(`<<<ARTIFACT …>>>`)과 기억(`<<<MEMORY …>>>`)도 흐름 출력에서 그대로 인식합니다.
  - 실행할 흐름은 **목록에서 고릅니다** — Runtime이 실행 중이면 *목록 불러오기* 로 그 Runtime에 저장된 흐름을 가져옵니다. Runtime이 꺼져 있으면 흐름 ID를 직접 입력해도 됩니다. 출력이 여러 개인 흐름은 *출력 컴포넌트* 로 어느 결과를 답으로 볼지 지정합니다.
  - 흐름은 Runtime 안에서 실행되므로 *작업 시 Runtime 시작* 이 켜져 있어야 저장됩니다. 대기열에 들어간 뒤 Pod가 없어서 실패하는 일을 미리 막기 위해 저장 시점에 확인합니다.
  - **흐름 안에서 일어나는 모델 호출은 플랫폼이 계량하지 않습니다.** 흐름의 컴포넌트가 직접 모델을 부르기 때문입니다. Runtime이 토큰 사용량을 보고하면 실행 기록 이벤트에 **보고된 값 그대로** 남기고, 플랫폼의 토큰 집계에는 넣지 않습니다.
  - 입력과 출력은 DLP 검사를 통과해야 합니다. 검사에서 막히면 흐름에 보내지 않고 작업이 실패하며(재시도하지 않습니다), 감사 로그에는 `dlp.flow` 로 남습니다.
- **승인 게이트**: *상태 변경 시 승인 필요* 를 켜면, 에이전트가 재시작·배포 같은 조치를 수행하기 전에 작업이 **승인 대기** 상태로 멈추고 검토자에게 알림이 갑니다. `검토` 화면에서 승인하면 승인 사유와 함께 작업이 이어서 진행되고, 거절하면 그 사유가 기록된 채 작업이 종료됩니다. 승인을 기다린 시간은 재시도 횟수로 계산되지 않습니다.
- **기억(Memory)**: 에이전트가 학습한 사실은 Pod가 재생성되어도 유지되며, 에이전트 상세 화면에서 확인하고 삭제할 수 있습니다.
- **위임(Delegation)**: 권한 밖의 일은 다른 에이전트에게 위임할 수 있습니다. 위임은 항상 작업 대기열을 거치므로 권한·쿼터·감사 기록이 그대로 적용되며, *최대 위임 깊이* 로 연쇄를 제한하고 순환 위임(A → B → A)은 자동으로 차단됩니다.
- **이벤트 Trigger**: 플랫폼에서 일어난 일에 반응해 작업을 시작할 수 있습니다. 구독 가능한 이벤트는 작업 완료·작업 실패·재시도 소진·승인 처리·런타임 장애·산출물 생성입니다. 이벤트 필터에 `{"agentId":"…"}` 같은 JSON 객체를 넣으면 해당 값이 일치하는 이벤트에만 반응하므로, 특정 에이전트나 런타임만 감시할 수 있습니다. 어떤 이벤트가 실제로 발행되고 있는지는 `작업` 화면의 *최근 플랫폼 이벤트* 에서 확인할 수 있습니다.
  - 이 Trigger가 만든 작업이 다시 같은 Trigger를 깨우지는 않으므로, 무한 반복 걱정 없이 연쇄를 구성할 수 있습니다.
  - **전달 보장**: 이벤트는 전달이 끝난 뒤에야 완료로 기록됩니다. 워커가 중간에 죽거나 작업 생성이 실패하면 이벤트는 그대로 남아 다시 시도되고(5초 → 10초 → 20초 …), 5회까지 실패하면 **전달 실패** 로 남기고 소유자에게 알림을 보냅니다. 조용히 사라지지 않습니다.
  - 구독자별로 전달 원장이 남기 때문에, 재전달이 일어나도 같은 Trigger에 같은 작업이 두 번 만들어지지 않습니다. `작업 대기열` 화면의 *최근 플랫폼 이벤트* 에서 `구독 N건 전달` · `재시도 대기` · `전달 실패` 상태와 어떤 Trigger에 전달됐는지 확인할 수 있습니다.
- **MCP 도구 정책**: 에이전트 상세 화면의 *MCP 도구 정책* 에서, 연결된 MCP 서버마다 호출 가능한 도구를 지정할 수 있습니다. *이 도구만 허용* 또는 *이 도구만 차단* 중에서 고르고 도구 이름을 쉼표로 나열하면 됩니다. 정책이 있는 서버는 Pod 안의 게이트웨이를 거쳐서만 호출되므로 에이전트가 우회할 수 없고, 차단된 도구는 도구 목록에도 나타나지 않으며, 자격 증명도 에이전트가 아닌 게이트웨이가 보관합니다. 정책 변경은 Runtime 재시작 후 적용됩니다.
  - *이 도구만 허용* 을 고르고 목록을 비워 두면 해당 서버의 모든 도구가 차단됩니다.
- **도구 실행 직전 승인**: 같은 화면의 *승인 필요 도구* 에 이름을 넣으면, 그 도구는 호출되는 순간 Pod 안의 게이트웨이가 붙잡아 두고 검토자가 승인할 때까지 실행되지 않습니다. 에이전트가 승인을 요청하지 않아도 마찬가지이며, 관리자 카탈로그에서 MCP 서버에 *승인 필요* 를 켜거나 위험도가 `high` 인 서버는(거버넌스의 *고위험 Tool 실행 승인* 이 켜져 있을 때) 모든 도구가 자동으로 대상이 됩니다.
  - 검토자는 `검토 · 승인` 화면에서 어떤 서버의 어떤 도구를 어떤 인자로 호출하려는지 보고 결정합니다. 승인하면 붙잡고 있던 호출이 그대로 진행되고, 거절하면 에이전트에게 거절 사유가 전달됩니다.
  - 승인 경로에 문제가 있으면(컨트롤 플레인에 연결할 수 없거나 대기 시간이 지나면) 호출은 **실행되지 않고** 차단됩니다. 승인 대기 기본 시간은 15분이며, 차단된 도구는 승인 대상으로 지정할 수 없습니다.
- **대화 작업을 백그라운드로 전환**: `런타임 세션` 화면에서 *백그라운드로* 를 누르면 지금 하던 일을 에이전트에게 맡길 수 있습니다. 이미 실행 중인 런타임을 그대로 사용하므로 작업이 도는 동안에도 같은 작업공간을 열어 볼 수 있습니다.
- **Runtime 예열**: 목표 설정의 *Runtime 예열* 에서 예약 실행 전에 Runtime을 미리 띄우고, 작업 후 잠시 유지하도록 설정할 수 있습니다. 예약된 작업이 콜드 스타트를 기다리지 않게 되고, 연속된 작업은 기동 비용을 한 번만 냅니다.
  - 예열된 Runtime은 사람이 시작·재시작하거나 작업공간을 열면 그 즉시 사용자 소유가 되어 자동으로 꺼지지 않습니다.
  - 대기 중인 작업이 남아 있으면 유지 시간이 지나도 중지하지 않습니다.
- **워커 자동 확장**: 대기열이 밀리면 워커가 동시 실행 수를 스스로 늘리고, 한가해지면 다시 줄입니다. 범위는 배포의 `AGENTHUB_WORKER_CONCURRENCY`(하한)와 `AGENTHUB_WORKER_MAX_CONCURRENCY`(상한)로 정하며, 두 값이 같으면 기존처럼 고정됩니다. 축소는 실행 중인 작업을 중단하지 않고 끝날 때 반영됩니다. 현재 대기·실행·워커 수는 `작업` 화면 상단에 표시됩니다.
- **작업 추적**: `작업 대기열` 화면에서 대기열·진행 상황·재시도·산출물을 확인하고, 실패한 작업은 다시 실행할 수 있습니다. 화면 상단의 **사용법 안내**에 아래 흐름이 요약되어 있고, 상태 칩에는 각 상태가 무슨 뜻인지 함께 표시됩니다.
  1. **작업을 맡깁니다.** `새 작업` 에서 에이전트와 할 일을 적습니다. 예시 버튼으로 작업 내용을 채워 볼 수 있고, 내용을 비우면 에이전트에 설정된 목표만으로 실행됩니다. 우선순위는 워커가 가져가는 순서만 정합니다.
  2. **워커가 가져갑니다.** 우선순위 순으로 가져가며, 필요하면 그 에이전트의 런타임을 자동으로 띄웁니다. 상단의 `대기 · 실행 · 워커` 숫자가 현재 상태입니다.
  3. **진행을 따라갑니다.** 상태 칩으로 걸러 보고, 각 행의 `실행 기록` 에서 계획·단계별 수행 내역·산출물·토큰 사용량을 확인합니다. 목록은 5초마다 갱신되고, 끝난 실행은 더 이상 조회하지 않습니다.
  4. **막힌 작업을 처리합니다.** `승인 대기` 는 `검토 · 승인` 에서 승인하면 이어서 진행되고, `실패` · `처리 불가` 는 원인을 고친 뒤 다시 실행할 수 있습니다.
- **단계 이어서 재시도(체크포인트)**: 재시도는 처음부터 다시 하지 않고 **이미 완료한 단계 다음부터** 이어서 실행합니다. 같은 추론을 두 번 결제하지 않고, 이미 배포·위임·파일 쓰기 같은 부수효과를 낸 단계를 다시 실행하지도 않습니다. 승인 후 재개도 같은 방식으로 그때까지의 맥락을 그대로 이어받습니다.
  - 실행 기록에는 이어받은 단계 수가 표시되고(`이전 시도 N단계 이어받음`), 단계 번호는 시도가 바뀌어도 이어집니다.
  - 다시 실행 버튼을 누르면 **이어서 실행** 과 **처음부터** 중에서 고를 수 있고, 이어서 실행할 수 있는 단계 수를 함께 보여줍니다. 앞선 추론의 전제가 바뀐 경우에는 처음부터를 고르세요.
  - 에이전트 정의(지시문·목표)가 바뀌면 이전 단계는 이어받지 않습니다. 같은 단계를 다시 실행하면 문제가 되는 에이전트는 목표 설정의 *재시도 시 완료한 단계에서 이어서 실행* 을 끄면 항상 처음부터 실행합니다.
- **토큰 사용량과 비용**: `작업` 화면의 *최근 30일 토큰 사용량* 에서 에이전트별 입력·출력 토큰과 금액을 확인할 수 있습니다. 금액은 `관리자 · 리소스 · 모델 엔드포인트` 에 입력한 100만 토큰당 단가로 계산되며, 단가를 입력하지 않은 모델의 토큰은 금액에 포함하지 않고 **미산정** 으로 따로 표시합니다. 자율 실행은 사람이 보고 있지 않을 때 도는 만큼, 수렴하지 못하는 작업이 조용히 비용을 쓰고 있지 않은지 여기서 확인하세요.

### 사내 자체 런타임(custom) 연결

OpenCode·Hermes·Qwen Paw 외에 사내에서 직접 만든 에이전트를 올릴 때는 런타임 유형 `custom` 을 사용합니다. 이 유형에는 내장 어댑터가 없으므로 **시작 명령** 을 반드시 입력해야 합니다.

- **시작 명령**: 컨테이너에서 실행할 명령을 한 줄에 하나씩 입력합니다(예: `/usr/local/bin/my-agent`, `serve`, `--port`, `9000`). 쉘을 거치지 않으므로 따옴표·파이프·환경변수 치환은 동작하지 않습니다. 필요하면 이미지의 진입 스크립트에 넣으세요.
- **서비스 포트**: 런타임이 실제로 듣는 포트를 입력합니다. 비워 두면 기본 포트를 사용하며, 값이 맞지 않으면 Pod는 떠도 준비(Ready) 상태가 되지 않습니다.
- 시작 명령이 없으면 저장 단계에서 거절됩니다. 예전에는 이 경우 Pod가 이미지 기본 진입점으로 떠서 원인 없이 CrashLoopBackOff에 빠졌습니다.

### 10.3 Runtime 공통 환경 (파일 · 환경변수)
*System Settings ▸ Runtime Environment* 에서 **모든 Runtime Pod에 공통으로 들어갈 파일과 환경변수**를 한 번만 정의합니다. 사내 PyPI 미러(`/etc/pip.conf`), conda 채널(`/home/agent/.condarc`), npm 레지스트리(`/etc/npmrc`), 프록시 주소처럼 에이전트마다 반복할 필요가 없는 설정이 대상입니다.

- **파일**: 절대경로, 권한(기본 `0644`), 내용을 입력하면 Pod의 모든 컨테이너에 같은 경로로 **읽기 전용 마운트**됩니다. 자주 쓰는 예시는 버튼 한 번으로 추가할 수 있습니다.
- **환경변수**: `PIP_INDEX_URL`, `HTTPS_PROXY`, `NO_PROXY` 처럼 컨테이너 전체가 공유해야 하는 값을 넣습니다.
- **사용 토글**: 항목을 지우지 않고 잠시 끌 수 있습니다. 저장 후 **다음 Runtime 시작 또는 재시작** 시점에 반영되며, 이미 실행 중인 Runtime은 Pod가 교체될 때 적용됩니다.
- **저장하면 즉시 반영됩니다**: 실행 중인 Runtime의 정의를 다시 써서 바로 적용하고, 내용이 실제로 바뀐 Pod만 새 설정으로 재시작합니다. 중지된 Runtime은 다음 시작 때 적용됩니다. 저장 후 화면에 "런타임 N개에 적용했습니다"처럼 결과가 표시됩니다.
- **"CRD가 오래되었습니다" 라고 나오면**: 클러스터의 `AgentRuntime` 정의가 컨트롤 플레인보다 낮은 버전이라 Kubernetes가 이 설정을 조용히 버리고 있는 상태입니다. `kubectl apply -k deploy/kubernetes` 로 매니페스트를 다시 적용한 뒤 저장하세요. (이미지만 교체하고 매니페스트를 적용하지 않은 업그레이드에서 발생합니다.)
- **비밀값은 넣지 않습니다**: 내용은 ConfigMap으로 전달되므로 토큰·비밀번호는 개인 Secret이나 MCP Credential로 관리하세요. `/etc/agenthub`, `/usr/local/bin`, `HOME`, `PATH`, `OPENAI_*`, `AGENTHUB_*` 등 플랫폼이 쓰는 경로와 변수는 저장 단계에서 거부됩니다.

Runtime 이미지에는 `python`·`pip`(`/opt/agenthub/venv`)과 `conda`·`mamba`(`/opt/conda`)가 기본 포함되어 있고, ruff·pytest·httpx·pandas·openai 같은 코딩 에이전트가 바로 찾는 라이브러리와 typescript·tsx·prettier·pnpm이 함께 설치되어 있습니다. conda 환경과 pip/npm 캐시는 `/home/agent` 볼륨에 생성되므로 Pod가 재시작되어도 유지됩니다. 읽기 전용 루트 파일시스템 프로파일에서는 `python -m venv ~/.venvs/작업이름` 이나 `conda create -n 작업이름` 처럼 홈 또는 작업공간 안에 환경을 만들어 사용하세요.

### 10.4 실행 Quota (동시 실행 · 비용)
*System Settings ▸ Governance ▸ 실행 Quota* 에서 자율 실행이 쓰는 자원과 비용을 제한합니다. 모두 **0이면 제한 없음** 입니다.

- **사용자당 동시 실행 작업**: 한 사용자의 작업이 동시에 몇 개까지 실행될지 정합니다. 한도에 걸린 작업은 **대기**하며, 재시도 횟수를 쓰지 않고 앞선 작업이 끝나면 실행됩니다.
- **사용자당 토큰·비용 예산 (최근 30일)**: 예산을 모두 쓰면 새 작업은 **실패**로 기록되고 소유자에게 알림이 갑니다. 며칠 뒤에야 풀리는 한도를 기다리며 워커 자리를 잡고 있지 않기 위해서입니다. 이미 예산을 초과한 상태에서 작업을 만들면 API가 429로 즉시 거절합니다.
- **에이전트별 토큰 예산**: 에이전트 상세의 *목표 ▸ 실행 한도* 에서 지정합니다. 수렴하지 못하는 에이전트 하나 때문에 사용자의 다른 작업까지 멈추지 않게 합니다.
- 사용량과 남은 예산은 `작업 대기열` 화면의 *최근 30일 토큰 사용량* 패널 상단에 함께 표시됩니다. 단가가 없는 모델의 토큰은 비용에 잡히지 않으므로 토큰 예산을 함께 설정하는 편이 안전합니다.

### 10.5 분산 추적 (Observability)
*System Settings ▸ Observability* 에서 OTLP Collector 주소를 넣으면 API와 워커가 OpenTelemetry Trace를 내보냅니다.

- **무엇이 보이나**: 작업 시도 하나가 `task.execute` 스팬 하나이고, 그 아래에 추론 단계(`agent.step`, 단계별 토큰), 완료 판정(`task.evaluate`), 런타임 확보(`runtime.acquire`)가 붙습니다. 워크플로는 `workflow.run` 과 단계별 `workflow.step` 으로 남고, API는 요청당 한 스팬을 라우트 패턴 이름으로 남깁니다.
- **로그·화면과 연결**: 추적이 켜져 있으면 실행 기록과 로그에 표시되는 Trace ID가 수집기의 Trace ID와 같은 값이므로, 화면에서 본 실행을 수집기에서 바로 찾을 수 있습니다. 꺼져 있으면 기존 `task-…` 형식으로 유지됩니다.
- **비용**: 주소를 비워 두면 추적은 완전히 꺼지고 스팬을 만들지도 버퍼에 쌓지도 않습니다. 수집기가 없는 폐쇄망에서 이 기능 때문에 드는 비용은 없습니다.
- **적용 시점**: 설정은 시작할 때 읽으므로 API와 워커를 재시작해야 반영됩니다. 수집기 주소가 잘못돼도 서비스는 그대로 뜨고 추적만 꺼진 채 로그에 이유가 남습니다.
- 환경변수 `AGENTHUB_OTLP_ENDPOINT` 로도 설정할 수 있으며, 화면에서 켠 설정이 우선합니다.

### 10.6 운영 현황 (관리자)
*관리자 ▸ 운영 현황* 은 배포 전체를 한 화면에서 봅니다. 24시간 · 7일 · 30일 기간을 고를 수 있고, 모든 수치는 실행 기록에서 그대로 계산되므로 상세 화면과 항상 일치합니다.

- **상단 지표**: 실행 성공률, 실행 소요(중앙값 · p95), 대기열 깊이와 워커 수, 가장 오래 기다린 작업, 토큰과 비용.
- **조치가 필요한 항목**: 승격 대기 작업, 재시도를 소진한 작업, 미승격 상태로 게이트에 걸린 에이전트, 배달 실패 이벤트, 워커 없이 쌓인 대기열, 실패한 런타임, 단가가 없어 금액에 잡히지 않은 토큰 — 각각 처리할 화면으로 바로 이동합니다.
- **분해**: 사용자별 · 에이전트별 · 모델별 토큰과 금액, 일자별 막대. **CSV 내려받기** 로 정산용 파일을 받을 수 있습니다(Excel에서 한글이 깨지지 않도록 BOM이 포함됩니다).

### 10.7 로그 · 감사 (관리자)
*관리자 ▸ 로그 · 감사* 에서 서버 로그, 감사 이벤트, 승인 대기를 확인합니다. 감사 로그는 **수행자(이름 일부)** · **동작** · **결과** · **기간** 으로 검색하고 페이지 단위로 넘기며, 조건을 그대로 적용한 **CSV 내려받기** 를 제공합니다. 내려받기 자체도 감사 기록에 남습니다.

*관리자 ▸ 사용자 · 팀* 목록에는 계정별 에이전트 수, 최근 30일 작업 수와 실패 수, 토큰 사용량이 함께 표시되어 어떤 계정이 실제로 쓰이고 있는지 바로 확인할 수 있습니다.

### 10.8 정책 (Policy as Code)
![플랫폼 정책](screenshots/35_admin_policy.png)

*관리자 ▸ 정책* 에서 사용자·에이전트·MCP 도구·데이터 등급을 대상으로 한 규칙을 한곳에 정의하고, 플랫폼이 직접 강제합니다.

- **위에서 아래로, 처음 맞는 규칙이 결정합니다**(방화벽과 동일). 좁은 예외(허용)를 넓은 차단 위에 두면 그 예외가 이깁니다. 화면에서 규칙 순서를 위/아래로 옮길 수 있습니다.
- **비워 둔 조건은 전체를 뜻합니다.** 규칙은 자신이 채운 조건이 **모두** 맞을 때 적용됩니다. 도구 이름은 끝에 `*`를 붙여 `delete_*`, `github/delete_*`처럼 쓸 수 있습니다(대소문자 무시).
- **강제 지점**: 작업 생성, 런타임 시작은 API에서 즉시 403으로 거절하며 **규칙에 적은 사유와 규칙 ID를 함께** 보여 줍니다. MCP 도구 호출은 Pod 안의 게이트웨이에서 막히므로 에이전트가 우회할 수 없고, 차단된 도구는 도구 목록에도 나타나지 않습니다.
- **차단·승인 규칙에는 사유가 필수**입니다. 거절된 사람이 무엇을 해야 할지 모르는 거절은 결국 문의로 돌아옵니다.
- **시뮬레이터**: 저장하기 전에 "이 사용자가 이 도구를 호출하면?"을 판정해 보고, 어떤 규칙이 결정했는지 확인합니다. 여러 규칙이 해당되면 순서까지 보여 줍니다.
- **JSON으로 편집**: 규칙 전체를 코드로 붙여넣거나 복사할 수 있습니다(형상 관리·리뷰용).
- 저장하면 실행 중인 런타임의 게이트웨이 설정까지 다시 쓰며, 도구 규칙이 바뀐 Pod만 재시작됩니다. 모든 차단은 감사 로그(`policy.*`)에 규칙 ID와 함께 남습니다.

### 10.9 런타임 설정 주입 (언어·시간대·제품 옵션)
![런타임 설정 주입](screenshots/38_admin_runtime_settings.png)

*관리자 ▸ 런타임 설정 주입* 에서 런타임 유형별로 설정을 정의하면, **기동·재기동할 때마다** 그 런타임이 읽는 설정 파일에 병합되고 환경변수로 주입됩니다.

- **환경변수**: 그 유형의 모든 컨테이너에 적용됩니다. 확인된 항목으로 `LANG`·`LC_ALL`(로케일), `TZ`(시간대), `HTTP_PROXY`·`HTTPS_PROXY`·`NO_PROXY`(폐쇄망 프록시)를 한 번에 넣을 수 있습니다. 플랫폼이 설정하는 변수(`AGENTHUB_*`, `OPENAI_*`, `PATH`, `HOME` 등)는 거절됩니다.
- **설정 파일 병합(JSON)**: 런타임이 읽는 파일에 키 단위로 병합됩니다. 객체는 키별로 합쳐지고 값·배열은 대체됩니다. 플랫폼이 만드는 키(`model`, `mcp`, `provider`, `mcp_servers`, Qwen Paw 공급자 설정)는 덮어쓸 수 없습니다 — 모델 연결과 도구 정책이 깨지면 플랫폼 장애처럼 보이기 때문입니다.
- **런타임별 주입 위치**: OpenCode는 `~/.config/opencode/opencode.json`, Hermes는 `~/.hermes/config.yaml`, Qwen Paw는 `qwenpaw init` 이후 `~/.qwenpaw/config.json` 에 병합됩니다. **Langflow는 설정 파일이 없습니다** — 모든 설정이 `LANGFLOW_*` 환경변수이므로 이 유형에는 파일 병합 칸이 나오지 않고, 확인된 항목으로 `LANGFLOW_LOG_LEVEL`(기본값 error 라 처음에는 info 권장), `LANGFLOW_WORKERS`, `LANGFLOW_WORKER_TIMEOUT`, `LANGFLOW_DATABASE_URL`(사내 PostgreSQL 사용 시)을 제공합니다.
- **자주 쓰는 설정** 카드는 두 종류입니다.
  - **확인됨**: 플랫폼이 이미 쓰는 키이거나 운영체제가 정의하는 변수입니다. 한 번 클릭으로 추가됩니다.
  - **확인 필요**: 자동 승인(YOLO) 모드, 테마, 스킬 경로처럼 **키 이름이 런타임 제품 버전마다 다른** 항목입니다. 플랫폼이 임의로 키를 만들어 넣으면 "적용된 것처럼 보이지만 아무 일도 하지 않는" 설정이 되므로, 제품 문서에서 키를 확인해 직접 입력하세요. 넣은 뒤 파일에 반영됐는지는 아래 주입 상태로 확인할 수 있습니다.
- **주입 상태**: Pod의 초기화 컨테이너가 **자신이 쓴 파일을 되읽어** 어떤 키가 들어갔는지 컨트롤 플레인에 보고합니다(값은 보고하지 않습니다).
  - `적용됨` — 실행 중인 Pod가 현재 설정 버전으로 시작했습니다.
  - `이전 설정으로 실행 중` — 설정을 바꾼 뒤 아직 재시작되지 않았습니다. 재시작하면 적용됩니다.
  - `확인 안 됨` — 아직 보고가 없습니다(실패가 아닙니다).
  - `적용 실패` — Pod가 파일을 쓰거나 읽지 못했다고 보고했습니다. 상세 메시지가 함께 표시됩니다.
  - `일부만 적용` — 선언한 환경변수 중 일부가 컨테이너에 도달하지 않았습니다. 보고된 키의 `env-missing:` 항목이 어느 변수인지 알려 줍니다. 환경변수로만 설정하는 Langflow에서 특히 중요합니다.

> 보고는 "그 키가 런타임이 읽는 파일에 들어 있다"는 사실까지를 증명합니다. 그 값을 제품이 실제로 존중하는지는 제품의 동작이며, 그래서 키가 확실하지 않은 항목은 "확인 필요"로 구분해 둡니다.

### 10.10 내용 검사 (DLP)
![내용 검사 (DLP)](screenshots/36_admin_dlp.png)

*관리자 ▸ 내용 검사* 에서 모델 호출과 MCP 도구 호출에 섞인 개인정보·신용정보·자격증명을 찾아 가리거나 차단합니다.

- **탐지 등급**: 주민등록번호·사업자등록번호(체크섬 검증), 신용카드번호(Luhn 검증), 휴대전화번호, 계좌번호, 여권번호, 이메일, API 키·개인 키. 체크섬을 통과하지 못한 값은 보고하지 않습니다 — 헛경보를 내는 검사기는 결국 꺼지기 때문입니다.
- **처리 방식**: `검사 안 함` / `기록만`(무엇이 오가는지 파악용) / `가리고 전송`(값을 "[등급 삭제됨]"으로 치환, 모델 호출 권장) / `차단`(호출 거절, 외부 시스템에 쓰는 도구 권장).
- **검사 지점**: 모델로 나가는 프롬프트(그리고 선택 시 응답)는 컨트롤 플레인이, MCP 도구 호출의 인자(그리고 선택 시 결과)는 **Pod 안 게이트웨이**가 검사합니다. 도구 호출은 컨트롤 플레인을 거치지 않으므로 에이전트가 우회할 수 없는 자리에서 검사해야 합니다.
- **기록**: 감사 로그에 등급·건수·**마스킹된 예시**만 남습니다. 찾은 값 자체는 저장하지도 로그에 쓰지도 않습니다. `로그 · 감사`에서 `dlp.model`, `dlp.tool` 로 검색하세요.
- **정책과 함께**: 특정 에이전트·역할만 더 엄격하게 하려면 [정책](#108-정책-policy-as-code)에서 데이터 등급(`rrn`, `card` 등)을 조건으로 규칙을 만드세요. 검사에서 등급이 발견되면 그 규칙이 함께 판정합니다.
- **적용 시점**: 모델 호출은 저장 후 5초 안에, 도구 호출은 설정이 Pod로 전달되고 해당 Pod가 재시작된 뒤 적용됩니다. 차단된 작업은 재시도하지 않고 즉시 실패합니다(같은 프롬프트는 같은 결과이므로).
- **샘플로 확인**: 저장 전에 텍스트를 붙여넣어 무엇이 잡히는지, 전송될 내용이 어떻게 바뀌는지 확인할 수 있습니다. 붙여넣은 내용은 저장되지 않습니다.

### 10.11 실행 제어 (관리자)
*관리자 ▸ 실행 제어* 는 실행 플레인을 직접 다루는 화면입니다.

- **실행 중지 · 재개**: 업그레이드나 사고 때 사용합니다. 중지하면 워커는 새 작업을 가져가지 않고, **실행 중인 작업은 끝까지 진행**합니다. 작업 등록은 계속되므로 재개하면 밀린 일이 이어서 실행됩니다(최대 5초 안에 적용). 중지 사유는 모든 사용자의 `작업 대기열` 화면에도 표시됩니다.
- **워커**: 각 워커가 10초마다 보고하며, 45초 이상 조용하면 **응답 없음** 으로 표시됩니다. 정상 종료한 워커는 "중지됨"으로 남아 크래시와 구분됩니다.
- **멈춘 작업 회수**: 워커가 죽으면서 들고 있던 작업은 30초 주기로 자동 회수되어 대기열로 돌아갑니다. **지금 회수** 로 즉시 처리할 수도 있습니다. 이미 소모한 시도 횟수는 그대로 유지됩니다.
- **작업 일괄 재실행**: 원인을 고친 뒤 *처리 불가* 또는 *실패* 작업을 한 번에 되돌립니다. 재시도 횟수는 0으로 초기화되며, 기간과 최대 건수로 범위를 제한합니다. 완료·취소된 작업은 대상이 될 수 없습니다.
- **배달 실패 이벤트 재배달**: 배달을 포기한 이벤트를 다시 큐에 넣습니다. 이미 성공한 구독자에게는 다시 배달되지 않습니다.
- **기록 보관 기간**: 작업·실행 기록·이벤트·감사 로그의 보관 일수를 정하면 워커가 매시간 정리합니다(0이면 보관). **미리보기** 로 삭제될 건수를 먼저 확인하세요. 감사 로그는 최소 30일, 실행 기록·작업은 7일, 이벤트는 3일 미만으로 줄일 수 없습니다.
